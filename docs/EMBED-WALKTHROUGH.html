The idea, in one paragraph

CareerCraft already fetches about 50 jobs or articles per search. To rank them by how well they fit this user, it sends the user's profile text and every item's text to Horus in one request. Horus turns each text into a list of numbers (an embedding). CareerCraft measures how close each item's numbers are to the profile's (cosine similarity) and adds that to the match score it already shows. Nothing is stored anywhere. Every search computes everything fresh, so there's nothing to go stale and nothing to clean up.

Words you'll meet in the code

Embedding / vector
A list of numbers (1,536 of them for the small model) that represents what a text means. Texts with similar meaning get similar lists, even with no words in common. That's why "AIN" can land near "Assistant in Nursing".
Cosine similarity
A single number that says how closely two vectors point the same way. 1 means identical meaning. In our tests, related jobs scored 0.45–0.75 and unrelated jobs 0.20–0.31. What matters is the ranking, not the raw value.
Dimensions
How many numbers are in each vector. The text-embedding-3 models are trained so that the first N numbers carry most of the meaning ("Matryoshka"). Asking for dimensions: 512 gives shorter vectors that rank almost as well, which means a much smaller response.
Token
The unit Azure bills by. Roughly 4 characters of English. Embeddings are charged per input token only.
Deployment
A named instance of a model inside an Azure AI account (for example, text-embedding-3-small). Your code calls the deployment by its name.
TPM / capacity
Tokens per minute: a speed limit on a deployment. Go over it and Azure returns 429 "too many requests".
Standard vs Provisioned
Standard bills only per token used, so an idle deployment costs $0 whatever its capacity. Provisioned (PTU) bills hourly whether used or not. Everything here is Standard.

Reading order

This follows the order things depend on each other: infrastructure, then config, then logic, then the HTTP edge, then the proof. Line numbers are as of 29 Sep.

Stop 1: the model deployment infrastructure/tofu/modules/foundry/main.tf : 148–170

151 resource "azurerm_cognitive_deployment" "embedding_small" {
152   count = var.deploy_embedding_small ? 1 : 0
      name  = "text-embedding-3-small"
      ...
      sku {
        name     = var.embedding_sku_name        # "Standard": billed per token
        capacity = var.embedding_small_capacity  # 350 = 350K tokens/minute
      }
      depends_on = [azapi_resource.realtime]
    }
  • count = … ? 1 : 0 is Tofu's on/off switch. The foundry module is used twice, for the US account and the AU account, and only the US one sets deploy_embedding_small = true (envs/dev/main.tf:38).
  • Capacity 350. One search is about 13–25K tokens, so the large deployment's 50K would start refusing calls at 2–4 searches a minute. 350K was the full quota available (checked with az cognitiveservices usage list -l eastus2), and on Standard, unused capacity costs nothing.
  • depends_on makes Tofu create deployments one at a time. Azure rejects two deployment changes on the same account at once.
  • Why a second deployment instead of switching the existing one: the knowledge search index was built from large vectors. Vectors from different models can't be compared, so the index has to stay on large.

Also look at modules/foundry/variables.tf:75–85 (the two new variables, with their reasoning in the descriptions) and outputs.tf / print-horus-env.ps1 (they surface the deployment name like every other one).

Stop 2: the model name in config packages/core/src/clients/openai.ts : 24

24   embeddingSmall: process.env.AZURE_OPENAI_EMBEDDING_SMALL_MODEL ?? 'text-embedding-3-small',

The default matches the deployment name from Stop 1, so Vercel needs no new environment variable. The env var exists only as an override. The client itself (getOpenAIClient, line 5) is shared: the same endpoint and key as everything else on the US account.

Four details are worth understanding here. Each one is a deliberate difference from the older helper in packages/core/src/knowledge/embeddings.ts, so open that file too:

  1. One request, not batches. The older embedTexts sends groups of 16 one after another (BATCH_SIZE = 16, line 9). For 51 texts that's 4 round trips added together, which is fine for background indexing but slow inside a user's search.
  2. Truncate to 2,000 characters. That's about 500 tokens: a job title plus the start of its description. JSearch returns full adverts, and the tail is benefits and boilerplate. Without the cap, cost goes up 5–10× and the ranking doesn't change.
  3. 8-second timeout, no retries. The OpenAI SDK's default is a 10-minute timeout with 2 retries. Worse, on a 429 it sleeps for Azure's Retry-After (up to 59 s) before retrying. CareerCraft has a fallback, so failing fast is better: the user sees results either way.
  4. vectors[item.index] places each answer by the index Azure reports instead of trusting arrival order. The verify script tests exactly this: the same text at positions 0 and 2 has to come back identical.

Where's the tenant isolation? There's no data to isolate, because nothing is stored or read. The tenant comes from the API key, never from the request body, and it's only used to attribute usage. That's the multi-tenancy rule applied to a stateless endpoint.

Stop 5: the proof scripts/verify-embed.ts

  • Line 45, cosine: the same maths CareerCraft will do. It's worth reading once to see it's just multiply-and-add.
  • Line 75, CASES: five scenarios. Each item is tagged related, adjacent or unrelated. The Australian-shorthand cases are there because they're where a smaller model is most likely to stumble.
  • Line 263, the pass rule: the lowest related or adjacent score must beat the highest unrelated score. That's a strict rule on purpose, because it's the property the match score depends on.
  • Line 278, response size: this is where the "always ask for 512 dimensions" advice comes from. On large, 3 MB at full width versus 469 KB at 512.

It calls the core helper directly, not the HTTP route, so it needs no API key. The route only adds auth, validation and metering on top.

Stop 6: the contract docs/CAREERCRAFT-INTEGRATION.md §10

This is what CareerCraft codes against: the request and response shape, the limits, "ask for 512", and the large-model baseline. If you change the route, change this too.

How we got here

  1. The plan came from the CareerCraft session. It designed the flow (profile → embed → cosine → MatchMeter) and asked two questions: small or large, and who writes the Horus side.
  2. Its assumptions were checked against this repo, and three were wrong: the env var name, the claim that /api/infer is metered (it isn't), and the small model being deployed (only large was).
  3. Small vs large: benchmarks show a small gap for this kind of task, the choice can be reversed per request, and small costs 1/6.5 as much per token.
  4. Cost check: idle Standard deployments cost $0. Your own bill proves it: 5 deployments, and the model charges only appear on days with actual use.
  5. A quota check changed the design: sharing the large deployment's 50K TPM would throttle at 2–4 searches a minute, so the small model got its own deployment with 350K.
  6. Tofu written. The plan showed exactly 1 to add. The apply was blocked by a permission check (correctly, since it changes live infrastructure), so it's yours to run.
  7. Core helper and route written, both typecheck, and they were verified live against large, because small doesn't exist yet.
  8. The route was rewritten underneath us by the other session. Its version didn't compile (embedTexts takes one argument), silently ignored dimensions, shared the large deployment, and had no timeout or metering. It was merged back, keeping its size guard, comments and count.
  9. The ranking cases were extended with Australian shorthand, adjacent roles and news. Large passes 5/5. The adjacent-roles margin is the tightest at 0.078, so that's the one to watch on small.
  10. A code review before publishing found six problems on the embed side, all now fixed: responses could exceed Vercel's 4.5 MB limit; model: 'large' let outside traffic onto the knowledge index's deployment; a single retry could sleep 59 s; deactivated tenants' keys still worked; an empty env var broke the model name; and the new env var wasn't declared.

Try it yourself

These make the code stick faster than reading alone:

  1. Run pnpm exec tsx scripts/verify-embed.ts --model large and match each printed section to the code that produced it.
  2. In section 4 of the script, change 512 to 256 and watch the size and time change.
  3. Add a case to CASES using a profile you know well, such as your own. Does the ranking match your gut?
  4. Run tofu -chdir=infrastructure/tofu/envs/dev plan and find the new deployment in the output.
  5. After the apply, run with --compare and read the two columns side by side.
Check yourself: why can't Horus's knowledge search just switch to small as well? Its index holds vectors made by large. A small-model query vector can't be compared with them, because they describe meaning on different "maps". Switching would mean re-embedding the entire corpus. The embed endpoint avoids this problem by storing nothing.
Check yourself: what happens to a user's search if Azure is down? embed() fails within about 8 s, and the route returns 502. CareerCraft's horusEmbed sees the failure, skips similarity, and ranks on the other signals. The page loads, and no error is shown.
Check yourself: why does the 350K capacity cost nothing? It's a Standard deployment, which bills per token processed. Capacity is only a ceiling on throughput, not something reserved and paid for. (Provisioned deployments are different, and none are used here.)
Check yourself: which tenant gets billed, and where does that come from? The tenant that owns the API key. It comes from validateApiKey (auth.tenantId), never from the request body, so a caller can't bill someone else.
